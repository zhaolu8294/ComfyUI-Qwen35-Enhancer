## 一、结论先说

**图片 prefill 慢的真凶是视觉塔入口的 `Conv3d`——它在 fp16/bf16 下是病态的，
不是算力问题，不是显存问题，不是量化问题，也不是缺 flash-attn。**

修法：把 `Qwen3VLVisionPatchEmbed.forward` 从 Conv3d 换成数学等价的 `F.linear`（GEMM）。
节点已自动完成，无需任何设置。

| 指标（同权重、同输入：2 张 543x768 / 581x768，max_image_side=768） | 修复前 | 修复后 | 倍数 |
|---|---|---|---|
| 视觉塔 forward | 29.30 s | **0.05 s** | **586x** |
| 整段 prefill（视觉塔 + LLM 1562 tok） | 30.33 s | **0.28 s** | **108x** |
| 生成阶段（prefill + 解码 92 tok） | 34.46 s | **4.64 s** | 7.4x |
| 整轮（含 4bit 量化加载 17s） | 66.58 s | **22.00 s** | 3.0x |

对上你 03:22 那次实机记录（73.27s）：**73.27s → 22.0s**。

> **线上确认（2026-10-07 04:1x，用户反馈）**：重启 ComfyUI 后按原工作流实跑，
> 整轮 **约 20 秒**。与基准台的 22.0s 吻合（差异来自当次图片尺寸/输出长度）。
> 至此该修复在真实使用路径上闭环，不再只是受控台架上的结论。

## 二、我上一轮的判断是错的，先认账

我上一轮说「Qwen3-VL 的视觉塔因为没装 flash-attn，退化成逐图切块 + Python 循环，
每视觉 token 33ms，这是 prefill 慢的根因」。

**这个结论被实测推翻了。** 源码里那条分支确实存在
（`modeling_qwen3_vl.py:223`，`is_flash_attention_requested` 为假时按图 `torch.split` 分块），
但它的代价被真正的大头完全淹没了 —— 装不装 flash-attn、用哪种注意力后端，
耗时几乎一模一样。

我为什么会判错：上一轮我只对比了「4bit vs bf16」和「有图 vs 纯文本」，
没有做**同权重、同输入、只换一个变量**的对照，就把相关性当成了因果。
这一轮补上了这个对照，结论立刻反转。

## 三、证据链

### 3.1 第一步：装了 flash-attn，但没用

按需求装好了 flash-attn（详见第五节），后端确认生效：

```
[Qwen35] 注意力后端：主模型 flash_attention_2 / 视觉塔 flash_attention_2
                    （请求 auto → 生效 flash_attention_2，flash-attn 2.8.3）
```

**但 prefill 仍是 30.43 s** —— 和没装时几乎一样。

### 3.2 第二步：控制变量 A/B，一刀切开「视觉塔 / LLM」

`bench_prefill_breakdown.py`：同一份权重、同一份输入，只把
`model.model.visual.config._attn_implementation` 换成三种后端
（`forward()` 每次调用才解析这个值，所以不用重新加载模型）。

```
视觉塔 eager             : 29.16s   占整段 96.1%
视觉塔 sdpa              : 28.91s   占整段 95.3%
视觉塔 flash_attention_2 : 29.30s   占整段 96.6%
LLM 部分（1479 tok）     :  1.02s   占整段  3.4%
整段 prefill             : 30.33s
```

**三种注意力后端毫无差别**（29.16 / 28.91 / 29.30）。这一条就把
「注意力后端 / flash-attn」这个方向彻底否掉了。

同时确认：**瓶颈确实在视觉塔**（占 96%），LLM 侧完全正常。

### 3.3 第三步：拆视觉塔内部

`profile_vision_tower.py` 把 forward 拆成 patch_embed / blocks / merger：

```
整塔 forward    : 29.33s
patch_embed     : 40.90s   ← 单独测比整塔还长，同一量级，锁定它
```

`Qwen3VLVisionPatchEmbed` 的实现很短：

```python
kernel_size = [temporal_patch_size, patch_size, patch_size]      # [2, 16, 16]
self.proj = nn.Conv3d(in_channels, embed_dim, kernel_size=kernel_size,
                      stride=kernel_size, bias=True)

def forward(self, hidden_states):
    hidden_states = hidden_states.view(-1, C, T, P, P)
    hidden_states = self.proj(hidden_states.to(dtype=target_dtype)).view(-1, self.embed_dim)
```

**kernel == stride ⇒ 输出空间尺寸恒为 1×1×1 ⇒ 数学上就是一个
`(N, 1536) @ (1536, 1152)` 的 GEMM**，约 12 GFLOP，4090D 上应该是 10ms 量级。

### 3.4 第四步：脱离模型做裸算子微基准（决定性）

`probe_conv_cases.py`：每档**独立子进程 + 60s 硬超时**（因为有的档会卡死，
普通串行跑法会被一个 60s 卡死拖垮整轮）。

| 档位 | 首次调用 | 稳态 | 结果 |
|---|---|---|---|
| Conv3d **fp32**（cuDNN 开） | 0.051 s | **4.4 ms** | ✅ 正常 |
| Conv3d **fp16**（cuDNN 开） | **> 60 s 未返回** | — | ❌ 卡死 |
| Conv3d **bf16**（cuDNN 开） | **> 60 s 未返回** | — | ❌ 卡死 |
| Conv3d **fp16**（cuDNN 关） | **> 60 s 未返回** | — | ❌ 卡死 |
| Conv3d **bf16**（cuDNN 关） | **> 60 s 未返回** | — | ❌ 卡死 |
| Conv3d **bf16**（benchmark 开，让 cuDNN 搜算法） | **> 60 s 未返回** | — | ❌ 卡死 |
| **等价 bf16 GEMM**（`F.linear`） | 0.079 s | **0.1 ms** | ✅ 极快 |
| Conv2d bf16（对照） | 0.049 s | 0.5 ms | ✅ 正常 |

三个关键点：

1. **只有 Conv3d 的半精度路径有病** —— 同一个算子 fp32 只要 4.4ms。
2. **与 cuDNN 的算法选择无关** —— 关掉 cuDNN、打开 benchmark 都一样卡死。
3. **等价的 GEMM 只要 0.1ms，比 fp32 卷积还快 44 倍。**

所以这不是「算法不够快」，是「走了一条根本不该走的路径」。
按计算量算，29s 对应理论 28ms —— **偏离 1000 倍，只能解释为路径病态**。

### 3.5 第五步：修复并实测

节点加载模型后自动替换 `Qwen3VLVisionPatchEmbed.forward`：

```python
def _gemm_patch_embed_forward(self, hidden_states):
    proj = self.proj
    n = hidden_states.shape[0]
    x = hidden_states.reshape(n, -1).to(proj.weight.dtype)          # 视图，不复制
    w = proj.weight.reshape(proj.out_channels, -1)                  # 视图，不复制
    return torch.nn.functional.linear(x, w, proj.bias)
```

安全性：

- **数学等价**：实测与原 Conv3d 的**最大绝对误差 2.1e-06**（fp32 CPU 对照）
- **不改权重**：`weight.reshape(...)` 是同一块内存的视图（`data_ptr()` 相同，已断言）
- **不破坏权重加载**：`state_dict` 键名仍是 `proj.weight` / `proj.bias`
- **幂等**：模块级标志，只补一次；二次调用返回 `False`
- **可关闭**：`QWEN35_NO_PATCH_EMBED_FIX=1` 保留原始 Conv3d
- 输出目录里会有 `视觉塔入口：patch_embed 走 等价 GEMM（已绕开 Conv3d 慢路径）`

修复后分段实测：

```
视觉塔 eager             : 0.13s
视觉塔 sdpa              : 0.06s
视觉塔 flash_attention_2 : 0.05s      ← 修复前 29.30s
整段 prefill             : 0.28s      ← 修复前 30.33s
```

有趣的是：**修复之后三种后端的差异才显出来**（0.13 / 0.06 / 0.05）。
换句话说，注意力后端确实有影响，但在 29s 的量级下这点差异根本看不见 ——
这也解释了为什么我上一轮会被误导。

## 五、现在还要不要调 `max_image_side`？

**不必再为 prefill 调它了。** 之前那套「边长每降一档 prefill 少 X 秒」的预测表
（1280→74s / 768→31s / 640→21s / 512→14s）是在病态路径下测出来的，
现在 prefill 只剩 0.28s，调分辨率的收益可以忽略。

`max_image_side=768` 仍是个合理默认（省显存），但不用为了速度牺牲它。

同理，之前建议的「跑扩写前腾空显卡」「关浏览器/桌面端」现在也不那么关键了 ——
prefill 已经不是瓶颈。**但显存仍要够**：不够时 `device_map="auto"` 会静默把层摊到 CPU，
解码从 26 tok/s 掉到 1 tok/s，这是另一个独立问题（节点有告警）。

## 八、方法论沉淀

1. **慢 ≠ 算法差。** 先算理论时间：29s vs 28ms，1000 倍偏离 → 一定是路径问题，不是算力问题。
2. **同权重、同输入、只换一个变量**，是唯一能证伪的手段。三种注意力后端耗时一致，
   一句话就把上一轮的结论否掉了。
3. **卡死也要测。** `subprocess` + 硬超时逐档跑，否则一个 60s 的卡死会拖垮整轮探测
   （实测 `torch.backends.cudnn.benchmark` 这类"试试看"的开关也可能卡死）。
4. **脱离模型做裸算子微基准。** 构造同形状的 Conv3d / Linear 换 dtype 逐个测，
   比在几十秒的模型里猜快两个数量级。
5. **单位成本比绝对值可靠。** ms/token 这类斜率一旦稳定，就能跨配置横向比较。
6. **用官方摘要做校验基准。** GitHub release API 的 `assets[].digest` 就是现成的
   sha256，不必"大小大致对上"就放过。

## 九、追加：换 Qwen3.5 后变慢 —— 补丁打在了别的类上

**时间**：2026-10-07 04:38　**触发**：用户切到 Qwen3.5-9B 后 prefill 又变慢。

### 9.1 现象（同机同参，只换模型）

| | 04:27 Qwen3-VL-8B | 04:32 Qwen3.5-9B |
|---|---|---|
| 加载类 | `Qwen3VLForConditionalGeneration` | `Qwen3_5ForConditionalGeneration` |
| 输入 | 2975 tok | 3001 tok |
| **prefill** | **0.69 s** | **75.61 s** |
| 折合 | ~0.3 ms/视觉token | **35.1 ms/视觉token** |
| 解码 | 24.9 tok/s | 23.1 tok/s |
| 视觉塔显存 | 1.1 GiB | 870 MiB |
| 整轮 | 40.25 s | 137.59 s |

**回归只发生在 prefill，解码一模一样。** 35.1 ms/视觉token 恰好就是没打补丁时的水平。

### 9.2 根因

补丁 v1 只做一件事：

```python
from transformers.models.qwen3_vl.modeling_qwen3_vl import Qwen3VLVisionPatchEmbed
Qwen3VLVisionPatchEmbed.forward = _gemm_patch_embed_forward
```

但 transformers 5.9.0 里 Qwen3.5 是**独立模块** `transformers.models.qwen3_5`，
类名叫 `Qwen3_5VisionPatchEmbed`。两者源码逐字相同：

```python
kernel_size = [self.temporal_patch_size, self.patch_size, self.patch_size]
self.proj = nn.Conv3d(self.in_channels, self.embed_dim,
                      kernel_size=kernel_size, stride=kernel_size, bias=True)
```

（depth 27 / hidden 1152 / patch 16 / temporal 2 / out 4096，Conv3d 权重形状
都是 `(1152, 3, 2, 16, 16)`）——**但类与模块都不同**，所以补丁补在了一个
根本不会被实例化的类上。

### 9.3 为什么日志没报警

`_PATCH_EMBED_PATCHED` 记录的是「**有没有给某个类成功打过补丁**」，
而不是「**当前这个模型实例被补了没有**」。Qwen3-VL 的类确实还在 transformers 里，
import 成功、赋值成功 → 标志位 True → 日志照报「已换成 GEMM」，
耗时提示还走进「已换成 GEMM 但仍偏贵：可能是图太多/太大」那条分支，
把人往错误方向引。**指标测错了对象，比没有指标更危险。**

### 9.4 修法：按结构识别，打实例

```
遍历 model.modules()
  -> 类名含 "patchembed"
  -> .proj 是 Conv3d 且 kernel==stride、padding=0、dilation=1、groups=1
  -> 替换该实例的 forward（幂等，打标记）
```

四个前提缺一不可：`kernel==stride` 保证输出恒为 1×1×1，
`padding=0 / dilation=1 / groups=1` 保证滑窗正好覆盖一次。
任一不满足就不替换 —— 宁可不动，也不能静默算错。
另加两道守卫：类名必须含 `patchembed`；展平维度对不上时直接 `RuntimeError`。

日志也改成按实例报：

```
[Qwen35] 视觉塔入口：patch_embed 走 等价 GEMM（本模型实例已替换 1 个，已绕开 Conv3d 慢路径）
```

找不到就转 `warning`，不再有机会"报成功但没生效"。

### 9.5 验证（`verify_qwen35_patch.py`，三层全过）

| 层 | 内容 | 结果 |
|---|---|---|
| A | 两族 patch_embed 结构一致、类对象不同 | 7 项通过 |
| B | **复现旧行为**：只补 Qwen3-VL 类后 Qwen3.5 确实漏网；实例级扫回来 | 18 项通过 |
| C | GPU 真实形状（8624 patch / 1536→1152） | **Conv3d bf16 超 60s 挂死；GEMM bf16 = 0.427 ms** |

数值等价：真实形状最大绝对误差 **5.36e-06**；权重仍是同一块内存视图；
`state_dict` 键名不变。`test_qwen35_v6_bilingual.py` 新增 M 段 14 项断言，
四套测试全绿。

### 9.6 这条教训比上一轮更重要

上一轮的错误是**判断错**（把 flash-attn 当瓶颈），被实验一枪打掉；
这一轮的错误是**修对了但对另一个模型无效**，而且**监控指标掩盖了失效**。

共同点：两次都是「按我熟悉的那条路径做完了，就认为对所有人都成立」。
所以现在补丁不认类名了 —— 类名是"我以为的名字"，结构才是"它实际是什么"。

| **加载扩写模型** | **23.05 s** | **44.4%** | 每轮重复付的固定开销 |
| 生成英文（prefill 1.59 + 解码 12.61） | 14.20 s | 27.4% | 真实计算 |

**结论：剩下 70% 已经不是算法问题，是配置选择问题。**

- `keep_model_loaded=true` → 连续跑时省掉每次 23.05 s 的加载
- `bilingual=off`（节点默认值）→ 不需要中文对照就省掉 13.26 s

两项都开 ≈ 51.85 s → **约 15 s**。**注意 `max_image_side` 现在完全不是杠杆了**：
图片预处理只用 0.05 s，prefill 只剩 1.59 s，调小它只会牺牲画质。

### 9.9 用户要求保留双语 —— 重新算剩余空间

`bilingual=off` 那条 13.26 s 的杠杆作废（用户明确要中文对照）。剩下：

| 环节 | 耗时 | 占比 | 能否动 |
|---|---|---|---|
| 加载扩写模型 | 23.05 s | 44.4% | **仅当本轮<u>不</u>跑 H3 时才值得省**（见下） |

| 中文解码 280 tok | 12.95 s | 25.0% | 用户要求保留 |

| 卸载 / 预处理 | 1.19 s | 2.3% | — |

#### 关于 `keep_model_loaded=true` 的重要限制

本项目的工作流是**扩写节点 → H3 视频生成同图串联**（日志可见：扩写结束后
04:56:06 立刻 `VAE load device: cuda:0` 开始装 H3 的 VAE）。

`keep_model_loaded=true` 会让 18.4 GiB 的扩写模型常驻显存，而 H3 侧要
staged 32427 MB + 25140 MB，24 GiB 卡上两者根本放不下 → H3 会被迫降级或换页。

**所以：**
- 反复调提示词、只跑扩写节点 → 开 `keep_model_loaded`，每轮省 23 s（51.85 → ~29 s）
- 扩写完直接出片 → **不要开**，这 23 s 是结构性成本

#### 真正剩下的计算地板

解码 21 tok/s（≈47.6 ms/token）对应有效带宽约 **378 GB/s**，
而 4090D 峰值约 1008 GB/s —— 只用到 37%。理论上还有空间，
但要先确认瓶颈到底在显存带宽、算子实现，还是每 token 的调度开销。
可试的对照（按代价从低到高）：`attention=auto`（换 FA2）、`quantization=8bit`
（权重字节减半）。**注意 8bit 只在显存带宽受限时才有收益**，
37% 的带宽利用率暗示瓶颈可能不在这里，得实测。

## 十、8bit 更慢 + 解码里的第二病灶：线性注意力的 torch 回退

**时间**：2026-10-07 05:0x　**触发**：用户试了 `quantization=8bit`，反馈反而更慢。

### 10.1 先认账：我上一轮推荐 8bit 的推理是错的

上一轮我写：「解码 21 tok/s ≈ 47.8 ms/token ≈ 有效带宽 378 GB/s，仅 4090D 峰值
(1008 GB/s) 的 37% → 若瓶颈是带宽，`quantization=8bit` 会有明显收益」。

**实测**（同模型同参数，只改量化）：

| | `none`（bf16）04:55 | `8bit` 05:05 |
|---|---|---|
| 权重放置 | cuda:0 17.5GiB，全 bf16 | cuda:0 11.1GiB（int8 6.4 + bf16 4.6） |
| 加载 | 23.05 s | 27.07 s |
| prefill（英文） | 1.59 s | 1.40 s |
| **解码** | **20.9 tok/s** | **6.3 tok/s** |
| 解码（英文 263→275 tok） | 12.61 s | **43.95 s** |
| 解码（中文 280→278 tok） | 12.95 s | **43.68 s** |
| **整轮** | **51.85 s** | **119.34 s** |

**8bit 让整轮慢了 2.3 倍，而且是纯粹的回归 —— prefill 没变，只有解码崩了。**

#### 错在哪

「带宽利用率低」**不等于**「提高带宽效率就能提速」。37% 的利用率恰恰说明
**瓶颈不在带宽**，那 8bit（把权重字节砍半）自然无从发力。更糟的是
bitsandbytes 的 `LLM.int8()` 会额外付出：

1. **离群列分解**：每次前向都要按阈值找出离群维度、拆成 fp16 子矩阵分开算；
2. **实时反量化**：int8 权重边用边解；
3. **int8 GEMV 在 batch=1 下效率差**：cublasLt 的 int8 路径对 batch=1 的小矩阵很不友好。

这三项开销在 batch=1 逐 token 解码时**远大于**省下的那点权重流量。
注意权重也没真的砍半：`int8 6.4GiB + bfloat16 4.6GiB`（embedding / lm_head /
norm / 视觉塔仍是 bf16），17.5 → 11.1 GiB，只有 1.58×。

**结论：这台机器上就用 `quantization=none`。bnb int8 是省显存的工具，不是提速的工具。**

### 10.2 顺着「瓶颈不在带宽」往下查，找到了真东西

既然解码不是带宽问题，那 47.8 ms/token 里除了 18.6 ms 的权重流下限，剩下的花在哪？

查模型的 config：

```
num_hidden_layers = 32
layer_types = ['linear_attention'] × 24 + ['full_attention'] × 8
full_attention_interval = 4
linear_num_key_heads=16  linear_num_value_heads=32
linear_key_head_dim=128  linear_value_head_dim=128  linear_conv_kernel_dim=4
mamba_ssm_dtype = float32
```

**Qwen3.5 是混合架构**：32 层里 24 层是 Gated DeltaNet 线性注意力。

再看 transformers 5.9.0 的 `modeling_qwen3_5.py`：

```python
if is_flash_linear_attention_available():
    from fla.modules import FusedRMSNormGated
    from fla.ops.gated_delta_rule import chunk_gated_delta_rule, fused_recurrent_gated_delta_rule
...
self.chunk_gated_delta_rule     = chunk_gated_delta_rule     or torch_chunk_gated_delta_rule
self.recurrent_gated_delta_rule = fused_recurrent_gated_delta_rule or torch_recurrent_gated_delta_rule
if not is_fast_path_available:
    logger.warning_once("The fast path is not available ... Falling back to torch implementation.")
```

本机 `fla` 与 `causal_conv1d` **都没装** → 四个符号全为 None → **24 层全部落到
torch 回退**：

```python
def torch_recurrent_gated_delta_rule(...):
    query, key, value, beta, g = [
        x.transpose(1, 2).contiguous().to(torch.float32) for x in (...)   # fp32
    ]
    for i in range(sequence_length):        # 逐 token
        last_recurrent_state = last_recurrent_state * g_t
        kv_mem = (last_recurrent_state * k_t.unsqueeze(-1)).sum(dim=-2)
        ...
```

**fp32 + 逐个 token + 一串小张量算子。**

### 10.3 定量（4090D，同权重同形状，seq=1）

| | 单层 | ×24 层 | 占解码 |
|---|---|---|---|
| **torch 回退**（真层前向） | 1.009 ms | **24.21 ms/token** | **50.6%** |
| **fla 融合内核**（真层前向） | 0.659 ms | 15.81 ms/token | 33.0% |
| torch 回退（裸 gated delta rule） | 0.321 ms | 7.71 ms | 16.1% |
| fla 融合内核（裸 gated delta rule） | 0.056 ms | 1.34 ms | 2.8% |

**等效带宽只有峰值 1008 GB/s 的 1.2%** —— 完全是「小算子太多」的延迟问题，
不是算力、不是带宽。**所以调 `max_image_side` 或换量化都救不了它。**

装 fla 后 24 层从 24.21 → 15.81 ms/token，**省 8.4 ms/token**：
解码 47.8 → 39.4 ms/token（20.9 → 25.4 tok/s），整轮 51.85 → 约 47 s。

### 10.6 我这一轮又踩的坑：把位置参数传错了

第一版 A/B 脚本报出「fla 快 4.3×」，**是错的**。原因是我用位置参数调用：

而 fla 的真实签名是：

`beta` 落进了 `gk` 槽位、`st` 落进 `gv`、`True` 落进 `beta` → 输出 `nan`，
耗时不成立。**这是我自己测试写错，不是 fla 的问题。**（transformers 自己的调用点

### 10.7 这一轮的教训

共同点还是同一条：**得出数字之后，先问「这个数字有没有可能是我自己引入的」。**
所以这一轮所有关键结论都做了交叉验证：裸算子 + 真层 + 多步漂移 + 调用顺序排查。

**① 8bit 是纯负收益，且量级很大。** none 18.5~21.1 → 8bit 2.3~6.4 tok/s，

一次性/间歇性开销（冷启动、页表、或上面那个分解路径）衰减掉了。

### 11.3 我上一轮的推理错在哪（第二次同类错误）

上一轮我写：「解码 21 tok/s ≈ 47.8 ms/token ≈ 等效带宽 378 GB/s，只用到峰值
1008 GB/s 的 37% → 若瓶颈是带宽，`quantization=8bit` 应有明显收益」。

**方向正好反了。** 带宽利用率低，恰恰说明**瓶颈不在带宽**；既然不在带宽，
那把权重字节砍半自然无从发力。而 8bit 还额外付出了离群列分解 + 实时反量化 +
batch=1 的 int8 GEMV 低效 —— 这三项在逐 token 解码时远大于省下的流量。

这是本项目的第二类错误（第一类是「判断错」，见第九章）：
**「把一个观察到的数字，当成了因果链的起点」**。37% 是个事实，但它是
「不是带宽」的证据，却被我当成了「带宽有空间」的证据。

### 11.4 顺带修掉的两个「指标测错对象」

**① 默认值就是 8bit。** `INPUT_TYPES` 里 `{"default": "8bit"}` ——
也就是说**任何一个新建节点都会默认落在最慢的档位上**。已改成 `none`。

**② 解码慢的归因一直是错的。** `_decode_speed_warning()` 原来无条件说
「这是『有层被摊到 CPU / 显存不足换页』的典型特征」，可 05:30 那次的权重分布是
`cuda:0 11.1GiB`，**一层都没落在 CPU 上**。它在把人往「腾显存」的死路上引。

现在改成三层归因，按「最该先修」排序：

```
1) _CPU_OFFLOAD_GIB > 0        → 硬故障，先腾显存
2) 层全在 GPU 但用了 bnb 量化  → 报出 none/8bit 实测对照，叫改回 none
3) 两者都不是                  → 承认原因不在已排查范围内，不硬编一个解释
```

第 3 层是刻意留的。**宁可说「我不知道」，也不给一个听起来合理却指错方向的说法** ——
这正是第九章「指标测错对象比没有指标更危险」的同一条教训，只是这次是文案层。

顺带把提示线也修了：`_SLOW_DECODE_TOK_S` 从 5.0 提到 12.0
（9B bf16 正常 18~22 tok/s，原阈值 5.0 会把 6.1/6.3 这种明显偏慢的值判为正常），
`_LINEAR_ATTN_SLOW_DECODE_TOK_S` 从 30.0 降到 15.0
（原值高于正常值，正常跑完也会刷这条提示）。测试里那两条断言原本拿
263tok/12.61s ≈ 20.9 tok/s 当「偏慢」来测 —— **那是 bf16 的正常速度**，
等于把提示线划在了正常值之上，一并修掉。

## 十二、"8bit 怎么优化" —— 实测答案：改 threshold 只是少亏，真正该换 4bit

**时间**：2026-10-07 05:5x　**触发**：用户问「8bit 怎么优化呢」。

### 12.1 先说清楚这轮**没能**做什么

想做的是加载真实 9B、直接量各量化档的解码 tok/s。**做不到**，两次尝试都失败：

| 尝试 | 结果 |
|---|---|
| 8bit 加载 | `OSError 1455 页面文件太小` —— 在 `safe_open()` mmap 18GB safetensors 时炸 |
| 4bit 加载 | 走到 `Loading weights: 0%| | 0/760` 后**段错误退出（139）** |

原因是**系统内存**而不是显存：`GlobalMemoryStatusEx` 实测
**物理内存 63.8GB 只剩 4.9GB 可用**（ComfyUI 单进程工作集约 29GB），
提交限额也只剩 18.6GB。同时显存其实有 21GiB 空闲（`torch.empty(12GiB)` 分配成功，
nvidia-smi 报的 1.66GB 不可信）。

→ 所以改用**真实层形状、随机权重**做受控对照。投影的成本只取决于
**形状 + 调用次数 + dtype**，不取决于权重数值，所以这条路对"哪个档更快"是有效的；
但它对"真实激活下的离群列分布"不忠实 —— 这一点在 12.5 里明确标出。

### 12.2 第一版基准不可重复，差点又踩同一个坑

顺序测各变体，两次运行结果互相矛盾：

| 项 | 第一次 | 第二次 |
|---|---|---|
| MLP 的 4bit | 5.73 ms | 12.70 ms |
| 全注意力 int8 t=0.0 | 4.07 ms | 12.69 ms |
| **bf16（对照）** | **784 GB/s** | **794 GB/s** |

bf16 两次都稳定 → **GPU 没问题，抖动来自 bnb 路径自身**（叠加桌面合成 /
ComfyUI 常驻的背景负载）。这与之前 `bench_conv3d` 那次 0.887 vs 0.321 ms
是同一类污染。

→ 改成**严格 A/B 交替法**（`bench_qwen35_proj_ab.py`）：同一批形状下同时持有
bf16 与候选，每个 pass 内背靠背交替计时，反复 5 轮、各取最小值，只报比值。
bf16 在三个组、两个 batch 下复现为 754/757/759、736/737/736、855 GB/s —— 稳定了。

### 12.3 结论一：`llm_int8_threshold` 是**算子二选一**，改成 0.0 稳快 1.7~1.9 倍

读 bnb 0.49.2 源码（`bitsandbytes/autograd/_functions.py:MatMul8bitLt.forward`）：

```python
if state.threshold > 0.0:
    output, subA = torch.ops.bitsandbytes.int8_mixed_scaled_mm(A, CA, state.CB, SCA, state.SCB, outlier_cols, bias)
else:
    output = torch.ops.bitsandbytes.int8_scaled_mm.default(CA, state.CB, SCA, state.SCB, bias=bias, dtype=A.dtype)
```

transformers 默认给 6.0 → **永远走上面那条（混合内核）**。

受控实测（相对 bf16，batch=1 / batch=256）：

| 组（调用次数） | int8 t=6.0 | int8 t=0.0 | 提升 |
|---|---|---|---|
| 线性注意力投影 ×24（120 次） | 5.62x / 3.45x | 3.23x / 1.82x | 1.7~1.9x |
| 全注意力投影 ×8（32 次） | 7.21x / 4.30x | 4.18x / 2.16x | 1.7~2.0x |

**且这是固定的算子选择收益，不是数据相关**：测试里 `threshold=0.0` 与 `6.0`
算出的数值误差**完全相同（8.065e-03）** —— 说明在这种情况下两者数学等价，
混合内核只是**更贵**，并不更准。（阈值 6.0 是**绝对值**，post-RMSNorm 激活 RMS≈1，
batch=1 时几乎挑不出离群列，`outlier_cols` 基本为空，内核仍然贵。）

代价要说清楚：0.0 之后离群列不再单独用 fp16 计算，改由「按列 absmax 缩放」承担，
该列其余数值精度下降 —— 也就是主动放弃了 LLM.int8() 论文里做无损的那部分。
对提示词扩写可接受；要保守可以给个较大的正数（如 20.0）。

### 12.4 结论二：int8 的根因是"没有余量可省"+"调用太碎"，调参救不回来

| 事实 | 数值 |
|---|---|
| batch=1 时 **bf16** Linear 等效带宽 | **754~855 GB/s**（4090D 峰值约 1008） |
| batch=1 时 **bnb int8** 内核实测带宽 | **44~117 GB/s** |
| Qwen3.5-9B 每 token 的 Linear 调用次数 | **约 248 次** |

三条叠加：

1. **bf16 已经在带宽极限附近** —— int8 砍一半字节的理论上限只有 2x，
   而它自己的内核效率低 6~10 倍，净亏。
2. **调用太碎**：24 层线性注意力 ×5 + 8 层全注意力 ×4 + 32 层 MLP ×3 = 248 次。
   最能说明问题的是**全注意力投影组**：只有 0.34B 参数（占 5%），
   int8 却慢 **7.21x** —— 慢的几乎全是每次调用的固定开销。
   其中 `in_proj_a` / `in_proj_b` 是 **Linear(4096, 32)**，131k 参数，
   24 层合计每 token 48 次调用 —— 量化它们纯属负担。已加入 skip 列表
   （代价约 12.6MB 显存）。
3. **混合内核**（见 12.3）。

### 12.5 结论三：真正"省显存不减速"的答案是 **4bit**

| 组 | bf16 | **4bit nf4** | 倍数 |
|---|---|---|---|
| **MLP ×32（4.83B 参数，占大头）** | 10.52 ms (855 GB/s) | **5.15 ms (437 GB/s)** | **0.49x** |
| 线性注意力投影 ×24 | 3.97 ms | 7.72 ms | 1.95x |
| 全注意力投影 ×8 | 0.85 ms | 2.03 ms | 2.39x |

按用户真实负载（prefill 3000 tok ×2 + decode 543 tok）加权：

| 档 | prefill ms | decode ms | 合计 | 相对 bf16 |
|---|---|---|---|---|
| bf16 | 701 | 8344 | 9045 | 1.00x |
| **4bit nf4** | 1152 | 8091 | 9243 | **1.02x** |
| int8 t=0.0 | 689 | 14324 | 15013 | 1.66x |
| int8 t=6.0（旧默认） | 1304 | 24864 | 26168 | 2.89x |

折算法：prefill 用 batch=256 的实测值 ×11.72（3000 tok）×2 段；decode 用 batch=1 的实测值 ×543 tok。
batch=1 逐项合计：**bf16 15.37 ms/token**（3.995+0.849+10.522）、
**4bit 14.90**（7.718+2.031+5.151）→ **0.97x** —— MLP 快一倍、小矩阵慢 2 倍多，两者相抵。
int8 的 MLP 组第二次运行显存不足（OOM），按同法第一次运行的比值外推
（t=6.0 → 1.64x、t=0.0 → 0.95x），已在表内标注。

> **勘误**：本节初稿的加权表误用了**第一次运行**的合计值
> （bf16 17.5 / 4bit 26.3 ms/token）—— 那正是 12.2 里被判定为不可靠的那组数，
> 会得出"4bit 比 bf16 慢 1.5 倍"的相反结论，与同页的 0.49x 自相矛盾。
> 现改用第二次严格 A/B 的值。这也再次说明**必须用可复现的那组数字**。

**4bit 在 decode 侧与 bf16 基本持平**（MLP 快一倍、小矩阵慢 2 倍多，两者相抵），
而显存从 17.5GiB 降到 **7.9GiB**（此处初稿写"约 5.5GiB"，是按权重字节估的，
真机实测 7.9GiB —— 见 13.3）；它的代价集中在 prefill（batch>1 时 1.6~3.5x），
而 prefill 在整轮里只占小头。

**这一条当时是外推，不是真机实测**：受 12.1 的内存限制，4bit 的真实整轮数字没拿到。
外推风险是已知的 —— 合成基准下 int8 t=6.0 的投影增量约 +30ms/token，
而真机日志里 8bit 比 bf16 多花约 +111ms/token，说明真实激活下 bnb 的代价比合成更大。
**结论"int8 不如 bf16"因此只会更强；但"4bit 与 bf16 持平"这一条需要用真机复核。**

> **已复核（2026-10-07，第十三章）**：真机 A/B 得到 `4bit` 整轮 **54.06s vs bf16
> 51.85s = 1.04x** —— **外推成立**。同一轮还拿到了 8bit 的整轮 71.01s，
> 并发现它的代价大头不在解码而在**加载**（+14.30s，占增量的 84%），
> 这是 12.4 那一节只盯算子做不出来的结论。

### 12.7 这轮的方法论教训

**"数字不可重复"本身就是一条结论，不能拿单次数字下判断。** v1 那两次互相矛盾的
结果如果只取一次，我会得出完全相反的结论（4bit 快一倍 vs 4bit 更慢）。
所以当对照项（bf16）稳定、而候选变体不稳定时，问题在候选变体身上 ——
这时唯一可靠的做法是**让它与对照项背靠背交替、多次取样取最小值**。

这也是本项目第三次遇到同类问题：`0.887 vs 0.321`（GPU 被 H3 抢占）、
本次 v1（bnb 自身抖动）。共同点都是"先测出一个数，再拿它当依据"。

## 十三、真机 A/B 定案：4bit 54.06s / 8bit 71.01s / none 51.85s —— 8bit 亏在**加载**

第十二章末尾留了一个未闭合项：「4bit 与 bf16 持平」是外推，需真机复核。
用户随后实跑了 4bit 与 8bit 两档（`4bit 54秒 8bit72秒`），这一章就是把这笔账结清。

### 13.1 数据来源与口径

`E:/AI/ComfyUI-aki-v3/ComfyUI/user/comfyui.log`，2026-10-07 **06:03（4bit）** 与
**06:09（8bit）** 两次，加上 `comfyui.prev2.log` 里 04:55 的 bf16 基线。
三次**同模型（huihui-ai_Huihui-Qwen3.5-9B-abliterated）、同工作流、同参数、
同一组参考图（906x1280 + 854x1280）**，只改 `quantization`。
8bit 那次已带本轮的两处改动（`llm_int8_threshold=0.0` + 新 skip 列表）。

| 档位 | 加载 | 卸载其他模型 | 图片预处理 | EN prefill | EN 解码 | ZH prefill | ZH 解码 | 卸载 | **合计** | 驻留 |
|---|---|---|---|---|---|---|---|---|---|---|
| `none` | 23.05s | 0.71s | 0.05s | 1.59s | 12.61s（263 tok / **20.9**） | 0.31s | 12.95s（280 tok / **21.6**） | 0.43s | **51.85s** | 17.5GiB |
| `4bit` | 19.60s | 0.78s | 0.34s | 1.41s | 16.51s（286 tok / **17.3**） | 0.32s | 14.59s（288 tok / **19.7**） | 0.40s | **54.06s** | 7.9GiB |
| `8bit` | 33.90s | 3.48s | 0.37s | 0.90s | 15.72s（195 tok / **12.4**） | 0.27s | 15.83s（207 tok / **13.1**） | 0.47s | **71.01s** | 11.1GiB |

（tok/s 一列是日志自己算的 `输出 token / 解码秒`。各档合计还含少量未单列的调度开销，
故分项相加与合计差 0.1s 左右。）

### 13.2 逐项差额分解 —— 增量不在解码

`4bit → 8bit`，整轮 **+16.95s**：

| 环节 | 4bit | 8bit | 差额 | 占增量 |
|---|---|---|---|---|
| **加载扩写模型** | 19.60s | **33.90s** | **+14.30s** | **84.4%** |
| 卸载其他模型 | 0.78s | 3.48s | +2.70s | 15.9% |
| 图片预处理 | 0.34s | 0.37s | +0.03s | 0.2% |
| EN prefill | 1.41s | 0.90s | **−0.51s** | −3.0% |
| EN 解码 | 16.51s | 15.72s | −0.79s | −4.7% |
| ZH prefill | 0.32s | 0.27s | −0.05s | −0.3% |
| ZH 解码 | 14.59s | 15.83s | +1.24s | 7.3% |
| 卸载扩写模型 | 0.40s | 0.47s | +0.07s | 0.4% |

两条必须讲清楚：

**① 「解码墙钟几乎持平」是假象，不能当成"8bit 解码不慢"。**
8bit 那次生成的 token 明显更少（EN 195 vs 286、ZH 207 vs 288，少约三成），
少生成的量正好抵消了每 token 的变慢。只有**每 token 速率**才是可比的：

| 口径 | bf16 | 4bit | 8bit |
|---|---|---|---|
| 解码合计 tok/s（543 / 574 / 402 tok ÷ 25.56 / 31.10 / 31.55 s） | **21.24** | **18.46（0.87×）** | **12.74（0.60×）** |
| prefill 吞吐（EN 段 3019 / 3044 / 3044 tok） | 1.90 ks tok/s | 2.16 ks（1.14×） | **3.38 ks（1.78×）** |

> **输出长度不同**本身是量化的副作用（数值变了 → 采样/EOS 时机变），不是速度。
> 跨档比"整轮秒数"时若不同时看 token 数，很容易得出相反结论 ——
> 这是本章最容易被误读的一处。

**② 「卸载其他模型 +2.70s」不是量化的属性，是运行顺序。**
4bit 那次开始前显存已有 22.5GiB 空闲（日志：`22.5GiB → 22.5GiB 可用`），
8bit 那次只剩 5.1GiB（要腾出约 17GiB 的 H3 资产，日志：`5.1GiB → 22.4GiB`）。
严格归给 8bit 的增量只有**加载的 +14.30s**。

### 13.3 显存口径修正

12.5 里写的"4bit 约 5.5GiB"是按权重字节估的，真机实测是 **7.9GiB**：

| 档位 | 分布（日志「权重分布」行） | 合计 |
|---|---|---|
| `4bit` | `bfloat16 4.7GiB` + `uint8 3.2GiB` | **7.9GiB** |
| `8bit` | `bfloat16 4.7GiB` + `int8 6.4GiB` | **11.1GiB** |
| `none` | `bfloat16 17.5GiB` | **17.5GiB** |

那份两组都有的 `bfloat16 4.7GiB` 是 embedding + lm_head（各约 2GiB，前者不是
`nn.Linear`、后者在 skip 名单里）加视觉塔 870MiB —— 量化真正能动的只有中间 6.6B 参数。
所以省显存倍率是 **2.2×（4bit）/ 1.58×（8bit）**，不是"砍到 1/4 / 1/2"。

### 13.4 由此产生的两处代码改动

| 改动 | 理由 |
|---|---|
| `_SLOW_DECODE_TOK_S` **12.0 → 14.0** | threshold=0.0 后 8bit 实测 12.4 tok/s，**正好卡在旧线之上** → 体检直接哑火。14.0 落在「4bit 最低 17.3」与「8bit 最高 13.1」之间的空档，既不误报 4bit、又能让 8bit 每次都触发 |
| 新增 `_decode_notes()`，**判为 8bit 主因时压掉 fla 建议** | 12.4 tok/s **同时**低于两条线（速度线 14.0 / 线性注意力线 15.0），日志会一边说"主因是 8bit"、一边建议"装 fla 省 1/3 解码"。后者不算错但量级差太远（fla ≈ +2 tok/s，换 4bit ≈ +5 tok/s 且显存砍一半），等于把人往次优解带 |

提示文案全部换成本章的真机数字（整轮 71.01 / 54.06 / 51.85、加载 33.90 / 19.60、
解码 12.4~13.1 / 17.3~19.7），并显式点出"还有一半代价在加载"。
v6 新增 **P 段 13 项**断言（含体检线必须卡在 13.1 与 17.3 之间、真机两档分别
该触发/不该触发、旧说法"慢 3~8 倍"已从源码清掉、互斥规则生效）。
全量 **228 项 v6 + patch 三层 + widgets 结构 + flash-attn 三层 + fla 等价** 全部通过。

### 13.5 结论

1. **4bit 的结论成立**：整轮 54.06s vs bf16 51.85s = **1.04×**，显存 7.9GiB vs 17.5GiB。
   12.5 那条外推**被真机证实**（每 token 是 bf16 的 0.87×，比外推的 0.97× 略差，
   但整轮仍在"基本持平"量级）。
2. **8bit 是纯负收益，且它亏在两处**：加载 +14.30s（84%）+ 解码每 token 0.60×。
   只调 `llm_int8_threshold` 能把它从 319s 拉回 71s，**但永远追不上 4bit 的 54s**。
3. **prefill 上 int8 反而最快（1.78× bf16）** —— 与"prefill 是算力瓶颈、decode 是
   带宽瓶颈"完全吻合，也是对 12.4「int8 在 decode 没有余量可省」的正面旁证。
   可惜 prefill 只占整轮 3%，救不回来。
4. **建议**：显存够 → `none`；需要省显存 → `4bit`；`8bit` 不再有任何使用场景。

## 十四、批量打标 8 tok/s 的真根因：**CPU 把线程调度到了 E-core**（实测 2.66 倍）

这一章回答用户那句「**批量打标慢了**」，也推翻了我前面几轮给过的两处错归因。
结论先放最前面，因为它是**可复现、可逆、已端到端验证**的因果结论，不是相关性。

### 14.1 结论

同一台机器、同一份模型、同一批图、同一配置，只改**进程 CPU 亲和性**：

| 实验 | 亲和性 | 输出 tok | 解码 s | **tok/s** | 相对 |
|---|---|---|---|---|---|
| A | 不限核（原始 28 逻辑核） | 542 | 76.6 | **7.1** | 1.00× |
| B | 只给 **P-core**（逻辑 0-15） | 542 | 28.8 | **18.8** | **2.66×** |
| C | 只给 **E-core**（逻辑 16-27） | 542 | 72.9 | **7.4** | 1.05× |
| D | 不限核 + 进程优先级 `HIGH` | 542 | 68.6 | 7.9 | 1.11× |
| E | 不限核 + 进程优先级 `ABOVE_NORMAL` | 542 | 63.2 | 8.6 | 1.21× |

**「不限核」与「只给 E-core」几乎一致（7.1 vs 7.4）** —— 也就是说 Windows 平时
就把这个解码线程丢在 E-core 上跑。把它限制到 P-core，速度立刻回到 18.8 tok/s，
**正好等于独立进程的 20.5~21.6**。连模型加载都同步变化：P-core 8.06s，不限核 15.40s。

端到端验证（3 张图，858 tok）：

| | 打标耗时 | tok/s | 整轮合计 |
|---|---|---|---|
| 修复前（不限核） | 117.68s | **7.3** | 135.48s |
| 修复后（钉 P-core） | **46.84s** | **18.3** | **56.87s** |

**整轮快 2.38 倍，解码快 2.51 倍。** 提高进程优先级**完全无效**（D/E 两档都没救回来），
唯一有效的手段是显式亲和性。

### 14.2 本机单核 P/E 性能比（说明 2.66 倍是"应该的"）

`bench_core_type.py`，`torch.set_num_threads(1)`，单核钉死后各跑 3 次取中位数：

| 微基准 | 单 P-core | 单 E-core | **P/E** |
|---|---|---|---|
| `py_int_loop`（Python 解释器紧循环） | 9,212,548 | 4,501,830 | **2.05×** |
| `small_linear`（反复派发 tiny `F.linear`） | 273,783 | 80,459 | **3.40×** |
| `alloc_loop`（反复创建小对象/小 tensor） | 948,275 | 216,159 | **4.39×** |

后两项**正是 HF 解码的负载特征**：每个输出 token 发约 3365 个 CUDA kernel
（平均只跑 17µs）、外加大量临时张量。实测的 **2.66× 正好落在这个区间中间**。
注意这不是主频差（E-core 4.3GHz vs P-core 5.5GHz 只值约 1.3×）——
是 E-core 在**细碎派发型**负载上的每算子后端开销被放大。

CPU：`Intel Core i7-14700KF`，8 P-core（HT → 逻辑 0-15）+ 12 E-core（逻辑 16-27）。
拓扑用 Windows 官方 `GetLogicalProcessorInformationEx(RelationProcessorCore)` 读
`EfficiencyClass` 判定（`EfficiencyClass 1` = 16 逻辑核 = P，`0` = 12 = E），
**不靠"前 16 个就是 P 核"这种硬编码猜测**。

### 14.3 为什么只有「批量打标（HF 路径）」中招

因为它的负载形态是 **进程内 + 单核 + Python 逐算子发射**，
所以"这个核是 P 还是 E"对它影响巨大。三条旁证：

* 同进程内 **Qwen3-VL-8B**（纯全注意力，无线性注意力层）同样 8.0 tok/s
  → 与模型架构无关，只要是 HF 路径就一样；
* **GGUF 后端不受影响**：`llama-server` 是**独立进程**，吞吐由 GPU 决定
  （同机 33.9~37.1 tok/s）。这也是为什么"校订"环节一直很快而"打标"很慢；
* 单个线程实测独占 **85~96% 的一个核**（Windows 每线程 CPU 计数，无采样偏差），
  整进程 92~98% —— 就是"单核受限"这个词的字面意思。

顺带解释了两个反复出现的现象：

1. **中途翻转、翻过去不回来**（prev.log 21:47 那轮：前 5 张 22.4 tok/s，第 6/7 张
   掉到 8.7/7.6；prev2.log 21:03 那轮方向相反）。线程在当前核上是 P 还是 E，
   是调度器的一次二元选择，一旦迁到 E-core 就会稳定留在那里。
2. **独立进程一直快**（20.5~21.6）。这个数与我们测到的 P-core 档 18.8 在噪声范围内
   一致，**但我没有直接量到独立进程落在哪个核**（`Process.cpu_num()` 在 Windows 上
   只能读当前进程，跨进程不支持）—— 这里标注为**未直接验证的推断**。

### 14.5 我这一轮**差点**又归错因（第二次同类错误，留档）

py-spy 采样显示监控线程 `Thread-8 (startMonitorLoop)`
（`ComfyUI-Crystools\general\monitor.py`）**占了全部样本的 52.7%**，
比真正解码的线程（36%）还高；独占时间第一名是 `ZwQuerySystemInformation`
（= `psutil.virtual_memory()` → `GetPerformanceInfo`），
而 Crystools 确实是 `CMonitor(1, ...)` **每秒轮询一次**。
看起来"监控抢 GIL"证据链完整。

**但它是伪影。** 用 Windows 内核维护的**每线程 CPU 时间**（psutil 可读，无采样偏差）
复核，解码期间的真相是：

```
tid3076  (prompt_worker 解码线程)      : 85~96%   ← 一个整核
tid50600 (startMonitorLoop 监控线程)   :  1~5%    ← 几乎不吃 CPU
进程合计                               : 92~98%
```

监控线程根本不吃 CPU。事后看，`py-spy` 当轮自己报了 `100s behind in sampling`，
采样本来就不可信；而我上一轮已经因为"证据不足就下结论"翻过一次车
（用户原话：「flash-linear-attention 之前米有装，也很快的」）。
**这次的规矩是：涉及"谁的 CPU"这类归属问题，一律以每线程 CPU 计数为准，采样器只作线索。**

顺带一个无关但值得记的量化：`psutil.virtual_memory()` 在本机单次耗时
**中位 5.55 ms**（`GetPerformanceInfo` 5.80 ms；而 `GlobalMemoryStatusEx` 只要 0.001 ms）,
`swap_memory()` 最大到过 254 ms。所以"每秒轮询一次"的成本约 6ms/s = 0.6% 的核，
即使不清理也远不足以解释 2.66 倍。

### 14.7 方法论教训：ComfyUI 会把「输入相同」的提交直接走缓存

第一版亲和性 A/B/C 全部返回了**逐字相同**的报告（542 tok / 73.46s），
而 B、C 的实际执行时间是 **0.02s / 0.04s** —— ComfyUI 的节点输出缓存
按 `(class_type, inputs)` 命中，第二轮直接复用了第一轮的结果。

**凡是"变化的东西不在节点输入里"的 A/B（进程亲和性、环境变量、外部状态），
都必须让输入本身也变一下**（本章用"每轮换一个临时目录"）。
更稳妥的做法是同时记录提交前的 `/history` key 集合，断言新 id 不在其中。
